# BetterSelf 内容规范

内容围绕 Unity 开发、C# 基础和 Unity × Android 工程实践组织。第一轮使用小规模示例验证写作、发布和复习流程，再将同一规范用于真实经验。

## 第一批示例

专题名称：C# 与 Unity 面试基础。

示例文章：《C# 值类型、引用类型与 Unity 中的分配问题》。文章需要清楚区分语言语义、内存分配与具体运行时行为，避免将“值类型”等同于“总在栈上”。

初步题目：

1. 值类型和引用类型的主要区别是什么？
2. 什么是装箱与拆箱？如何识别实际代码中的装箱？
3. string 的不可变性意味着什么？什么情况下考虑 StringBuilder？
4. Unity 的每帧逻辑中，如何查找反复发生的托管分配？
5. Unity 协程与多线程有什么区别？

这些是选题，答案在编写时根据 Microsoft 与 Unity 官方文档核验。使用与具体 Unity 版本相关的结论时补充环境说明；示例全部标注“示例内容”，实际项目经验另行提供。

## 知识文章模板

文章使用 Markdown，头部元信息包含以下字段：

| 字段          | 含义                                                          |
| ------------- | ------------------------------------------------------------- |
| id            | 稳定唯一标识，改名或调整目录时保留                            |
| title         | 标题                                                          |
| topic         | 所属专题展示名，独立于网站主分类                              |
| domainId      | `content/taxonomy.yaml` 中的稳定主题 ID                       |
| categoryId    | 主题内的稳定子分类 ID                                         |
| noteType      | concept / guide / troubleshooting / retrospective / resources |
| tags          | 主题标签                                                      |
| summary       | 简短摘要                                                      |
| updatedAt     | 最近内容更新时间，YYYY-MM-DD                                  |
| verifiedAt    | 最近核验日期；未核验时用 YAML `null` 或省略，不使用导入日期   |
| sample        | 是否示例内容                                                  |
| applicability | 适用语言、Unity 版本或运行环境                                |
| sources       | 官方文档与其他确实使用的来源                                  |

正文建议依次覆盖：

1. 要解决的问题与结论。
2. 核心概念与机制。
3. 最小代码示例。
4. 与 Unity 开发的联系。
5. 常见误区与适用边界。
6. 如何验证或进一步排查。

内容仍在理解或验证过程中时，明确标注状态，补充后继续修订。题目关联通过元信息或题库的 articleIds 完成。

涉及 Unity、Android 或其他工具的配置改动时，不能只写“关闭某功能”或只给序列化字段。每个关键配置至少写清：

1. 适用的引擎、包和平台版本。
2. Editor 或工具中的完整操作路径，以及界面字段名称。
3. 配置文件、序列化字段或 API 对应关系；无法可靠确认时明确不写。
4. 原值、新值和本次是否实际采用。
5. 配置控制的机制，以及它不控制哪些相邻功能。
6. 修改前提和可能出现的画质、性能、兼容性或维护问题。
7. 判断配置生效的步骤、对照条件和回归范围。
8. 恢复原值、重新构建或清理产物等回退步骤。

优先指导读者通过 Editor 或正式工具修改，序列化字段用于代码审查和生效核对。多个开关一起修改时要注明不能独立归因；同一项目存在多 Quality、平台资产、Renderer 或构建脚本时，先说明如何确认真正生效的配置。

## 面试题模板

题目来源使用 YAML，长答案支持多行 Markdown。每道题都有独立稳定 ID，方便记录学习状态和修改历史。

| 字段          | 含义                                  |
| ------------- | ------------------------------------- |
| id            | 题目稳定唯一标识                      |
| title         | 问题本身                              |
| topic         | 所属专题                              |
| tags          | 标签                                  |
| level         | 基础、原理或场景                      |
| shortAnswer   | 约 30 秒可说清的回答                  |
| explanation   | 详细说明与代码                        |
| pitfalls      | 常见错误理解                          |
| parentId      | 上一层题目 ID，主问题省略或为 null    |
| followUps     | 可点击的追问题目 ID，叶子题使用空数组 |
| articleIds    | 关联知识文章 ID                       |
| applicability | 适用版本与运行环境                    |
| updatedAt     | 最近内容更新时间                      |
| verifiedAt    | 最近核验日期                          |
| sample        | 是否示例内容                          |
| sources       | 参考来源                              |

每条追问必须有独立、稳定的题目 ID 与完整答案，禁止只填写没有答案的问题文字。父题通过 `followUps` 引用子题，子题通过 `parentId` 标记默认上一级；复用已存在题目时直接关联，不复制答案。内容校验阻止缺失、自引用、重复和循环关系。

复杂题按“场景与限制 → 已有证据 → 新增条件 → 方案取舍 → 验证与回退”逐步深入。教学场景标注示例，不能将参考答案包装为个人项目成果。招聘描述用于能力选题，技术结论仍以官方文档和实际证据为依据。

题目内容与个人掌握程度分开存储。每次学习由用户选择“不会／模糊／掌握”；查看答案本身只记录查看行为。

## 真实项目复盘模板

收到真实项目材料后，按下面的顺序整理：

1. 项目背景、环境与个人职责。
2. 问题表现、影响范围和衡量指标。
3. 排查过程及关键证据。
4. 根因与必要的机制说明。
5. 候选方案、选择理由及代价。
6. 实施结果与验证方法。
7. 可复用经验与关联知识。
8. 可以转化为面试追问的问题。

无法提供准确测量数据时，保留定性结果并说明验证方式。公开内容使用经用户确认可分享的信息，项目名称和业务数据可做必要概括。

## 新内容进入网站的流程

1. 按模板整理文章或题目。
2. 填写稳定 ID、专题、版本范围与实际来源。
3. 本地校验结构、重复 ID 与文章关联。
4. 预览排版和代码示例。
5. 发布新版。
6. 手机获取更新，检查对应内容和历史学习记录。

第一批示例使用过程中，优先调整影响写作和复习的模板字段；批量整理开始后保持 ID 和必要字段稳定。

## 分类与来源规则

每篇笔记只有一个主题和子分类，类型独立于主题。网站只展示有已整理内容的分类；原始有道路径、私人标题与迁移索引只放在被 Git 忽略的本地档案中。

外部来源沿用 `title` 与 HTTPS `url`，也可显式设置 `kind: external`。个人实践使用 `kind: personal` 与真实的 `title` 署名，不填写 `url`。例如：

```yaml
sources:
  - kind: personal
    title: 个人项目实践记录
verifiedAt: null
```

未核验内容会显示“内容尚未核验”。导出、排版与图片完整性检查不视为技术内容核验；适用环境和验证边界写在 `applicability`。

## 持续收录项目实践

性能排查、兼容性修复和工程问题统一按[项目实践收录方案](PRACTICE_KNOWLEDGE_PLAN.md)整理；使用[实践记录模板](templates/PRACTICE_RECORD.md)保留证据、验证边界与后续结果。先匹配已有笔记，原始资料留在本地整理区，确认公开范围后再接入正文。

公开合集在 `content/projects.yaml` 中使用稳定 ID、脱敏标题、简介、主题 ID 和文章 ID 列表。合集不复制正文，不填写内部路径、仓库、提交或真实项目名。
