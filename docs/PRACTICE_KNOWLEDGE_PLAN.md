# 从项目问题到可复用知识

日期：2026-10-26。状态：收录方案已落地，首批三篇脱敏内容已进入网站。

## 目标与本次安排

BetterSelf 作为跨项目的经验入口：遇到问题时能找到排查步骤、实施条件、验证方式和反例。项目代码、完整性能采样和构建制品继续由原项目管理。

首批选用一次 Unity Android 性能优化及一次手机固定 30 FPS 排查，整理成三篇可独立阅读的草稿：

| 稳定 ID                              | 笔记                                          | 主要用途                                                 |
| ------------------------------------ | --------------------------------------------- | -------------------------------------------------------- |
| `unity-mobile-performance-playbook`  | Unity 移动端性能优化：诊断顺序与复用清单      | 遇到新问题时选择排查路径；按症状寻找已做过的优化         |
| `unity-android-frame-pacing-case`    | Unity Android 固定 30 FPS：一次帧同步对照实验 | 区分计算开销、等待和实际显示帧率，理解设备相关结论的边界 |
| `unity-pooling-lifecycle-regression` | Unity 对象池复用：状态清理与相机跳变回归      | 设计池的所有权、清理顺序、首帧验证及异常场景             |

私有证据和本地草稿保存在 `.artifacts/practice/projects/<project-id>/<date>-<topic>/`。三篇脱敏稿已加入公开文章目录，并由 `content/projects.yaml` 组成“Unity 休闲游戏性能优化”项目实践合集。合集只使用脱敏名称，不包含原项目标识。

首批统一放在已有 `Unity / 调试与性能` 分类，通过 Android、URP、GC、Frame Pacing、缓存、对象池等标签交叉查找。资源主题将来有足够独立内容时再拆至 `Unity / 资源管理`，保持 ID 不变。

不新增“性能优化”一级导航。项目作为跨文章的次要维度：合集负责组合阅读，文章仍在通用技术分类中独立检索和更新。

## 后续每次问题的处理流程

1. **收集最小材料。** 用户给出本次对话、报错/截图/采样或相关提交即可。缺少的环境与指标标为未知，不要求用户重新抄写整段过程。
2. **先检索已有笔记。** 比较症状、机制、平台和版本；同一问题补证据，同一方法补案例。相似表象但机制不同的案例独立保留。
3. **建立本地记录。** 用[实践记录模板](templates/PRACTICE_RECORD.md)记录现象、假设、实验、结果、代价、回退及原件位置。未解决的问题也能收录。
4. **提出可检验的结论。** 每个结论附环境和证据；区分用户观察、采样测量、代码检查、自动回归与推断。实验失败或回退也保留原因。
5. **提炼复用内容。** 案例回答“这次如何定位”，指南回答“下次如何排查”，概念回答“为什么”。不把所有聊天按时间顺序拼成文章。
6. **检查公开范围后接入正文。** 本地稿去除私人路径、项目身份、内部仓库、设备标识、日志隐私和制品下载地址；获得相应公开授权后再进入 `content/articles/`。
7. **校验与预览。** 校验 ID、分类、来源和关联链接；预览表格、代码和手机阅读。发布仍是独立动作，进入整理区不等于发布。
8. **补充后续结果。** 新包测试、复现失败、版本升级或反例出现时更新原 ID、验证范围和结论，不重复新建一篇“最终版”。

同一案例可以先“代码已改、自动回归通过、真机性能待测”，以后再补手机结果。无需等问题完全解决才保存过程。

## 用两类状态描述，避免把“做过”写成“有效”

工作状态：`排查中 → 已实施 → 已归纳`，不再适用时标记 `已失效/被替代`。

证据单独记录，允许组合：

| 证据              | 能说明什么                             | 不能直接说明什么                 |
| ----------------- | -------------------------------------- | -------------------------------- |
| 代码/资源核对     | 修改确实存在，结构或调用路径已改变     | 真机一定更快                     |
| 自动回归通过      | 在所列测试条件下功能和状态符合预期     | 所有设备和玩法均正常             |
| Editor 局部基准   | 指定函数、运行时和冷热状态下的耗时变化 | 手机整段流程获得同样倍数收益     |
| 真机定性反馈      | 用户在该包和该设备观察到改善或正常     | 单个开关的独立贡献               |
| 真机对照测量      | 可比条件下指标发生变化                 | 跨设备通用、已定位到底层引擎缺陷 |
| 长时间/多设备验证 | 所覆盖范围内的稳定性                   | 所有未来版本永远有效             |

状态先用正文表格维护。`updatedAt` 是内容更新时间；`verifiedAt` 只在确有核验时填写，适用范围必须与日期一起更新。结构校验通过、导入日期和排版完成不等于技术验证。

## 复用与去重规则

- 保留稳定 ID，重命名、补充或迁移目录不新建学习记录。
- 多个案例支持同一方法时，更新方法笔记并链接案例；保留每次环境差异。
- 只将确有独立问题、回答和追问的内容转成题目；普通知识文章不强制题库化。
- 同名或同为“30 帧”不自动合并；渲染过重、目标帧率设置和提交等待可以产生相近表象。
- 发现旧结论不成立时，在原结论旁标明反例、失效版本及替代方案，保留变更原因。
- 默认提炼思路、检查项和回归模式。通用代码应在至少两个真实使用场景验证后再考虑抽库；不把游戏业务类直接复制为“通用优化库”。

## 与成长计划结合

首批内容适合现有第 11 周的性能基线、第 17 周的真实案例和第 18 周的对照/回归训练。“真机性能与稳定性”案例已关联公开项目实践合集及三篇文章。

`unity-case-performance` 已有“环境是否一致、证据是否支持结论、怎样回归”的提示，可用帧同步案例组织个人讲述；对象池案例补充设计取舍与回归意识。私人草稿由用户选择填入，不用仓库内容覆盖浏览器已保存的记录。

## 可以直接复用的收录指令

> 把这次问题和解决方案沉淀到 BetterSelf。先检索已有笔记：同一问题补充原记录，新的机制再建案例。整理现象、环境、关键证据、方案与代价、测试结果、适用边界和回退方式；缺少的数据标为待验证。原始资料留在本地整理区，公开文章与发布按已有授权范围处理。只有适合练习的内容才提炼面试题，不自动加入复习。

也可以只说“按实践收录流程整理这次问题”，并提供本方案路径。每次收录输出：新增/更新了什么、证据在哪里、哪些结论仍待验证。
